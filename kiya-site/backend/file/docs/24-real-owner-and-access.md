# ۲۴ — مدیر کل واقعی و کنترل تیم

تاریخ2026-10-22 · نسخه0.4.0 · شاخهarena/f6a09f64-webkiya.

در پاسخ به درخواست مالک، حساب OWNER واقعی روی PostgreSQL محلی همین محیط ساخته شد؛ شناسهٔ شخصی و رمز عمداً در این گزارش نیست. رمز فقط scrypt با salt تصادفی است؛ هیچ شماره‌ای به‌دروغ phoneVerified علامت نخورده و هیچ MFAای از طرف مالک دور زده یا از قبل تنظیم نشده است. مالک باید خودش در `/admin` Authenticator تنظیم و recovery-codeها را امن ذخیره کند. رمز ارسال‌شده در چت پس از ورود تغییر داده شود؛ ابزار تغییر رمز با رمز فعلی/MFA در پنل وجود دارد. این عمل حساب محلی ساخته، نه انتشار دامنه یا انتقال دادهٔ خصوصی به Git.

## کد اجرایی تازه
- CLI bootstrap با phone اختیاری معتبر، همان محدودیت یک‌بار و رمز محیطی. هیچ seed پیش‌فرض یا reset پنهان برای مالک ساخته نشده است.
- ورود با شناسه/موبایل ثبت‌شده؛ ارقام فارسی/عربی و پیشوند09/+98/0098 نرمال می‌شوند و rate-limit شناسهٔ معادل مشترک دارد. اتصال SMS همچنان خاموش است.
- migration004: Role.version و مجوزهای staff:manage/role:manage برای OWNER. custom role نمی‌تواند مجوز IAM بگیرد؛ حتی مجوز دستیِ بدون عضویت OWNER از API عبور نمی‌کند.
- GET /api/admin/access، POST/PATCH roles و staff: ساخت حساب پرسنلی واقعی، نقش عملیاتی سفارشی، ویرایش نقش، تخصیص نقش، فعال/غیرفعال‌سازی و ابطال نشست‌ها. ارتقای OWNER نیازمند ownerConfirmed صریح است؛ کلیدهای نقش سفارشی را سرور تولید می‌کند. نقش‌های پایه از این API قابل ویرایش نیستند.
- تغییرات IAM با advisory lock مشترک، lock حساب actor، بررسی مجدد session/MFA/active/version/membership داخل transaction، optimistic version و audit اتمیک. رقابت دو مدیر کل برای تعلیق یکدیگر نمی‌تواند هر دو را از بین ببرد. آخرین OWNER فعال و عدم ویرایش وضعیت/نقش خود محافظت می‌شوند.
- تغییر رمزِ خود، با رمز فعلی + MFA و حداقل۱۴نویسه؛ credential-version و همهٔ sessionها باطل می‌شوند. hash، plaintext، MFA seed و کد بازیابی وارد audit یا DTO نمی‌شوند.
- UI بخش تیم برای مدیر کل واقعی، به‌علاوه امنیت حساب من برای STAFF دارای MFA. نمای عمومی فقط‌خواندنی هنوز کاملاً جداست؛ فرم‌های IAM در آن وجود ندارند.

## شواهد و مرزها
۳۲ تست backend واقعی PostgreSQL و ۸ E2E؛ ۹ integration تازه برای مالک/MFA، مقابله با IAM جعلی، role/staff CRUD محدود، version/revocation، owner race/last-owner، phone normalization و تغییر رمز. E2E تازه از ورود/TOTP یک مالک موقت شروع و ساخت نقش/پرسنل، کاهش دسترسی و ابطال session، تعلیق و تغییر رمز را در مرورگر انجام می‌دهد؛ فقط fixture موقت خود را پاک می‌کند، نه حساب مالک محیط. integration فقط DB مجزای kiya_test را پاک می‌کند.

Scopeهای کالا/انبار، دعوت امن یک‌بارمصرف، انقضای رمز اولیه/forced rotation پرسنل، حذف نقش/حساب، reset MFA، workflow اختصاصی انتقال مالک، step-up کوتاه‌عمر و ممیزی مستقل هنوز پیاده نشده‌اند. فهرست تیم سقف۱۰۰ دارد؛ مجوزها سراسریِ عملیاتی‌اند، نه row-level scope. نقش پایهٔ مالک با انتخاب آگاهانه قابل تخصیص است؛ مدیریت سیاست خود OWNER از UI ممنوع است.

فروشگاه هنوز SKU/پک/BOM/stock/order/payment تولیدی و provider واقعی ندارد. اسناد قبلی snapshotهای تاریخی‌اند؛ این ادامه اعلام تکمیل FULL یا امنیت production نیست. DB محلی هنوز credential مالک DB دارد و به runtime-role حداقلی، backup/restore و پایش تولید نیاز دارد.
