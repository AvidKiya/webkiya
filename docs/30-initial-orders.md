# گزارش۳۰ — رزرو اتمیک و سفارش اولیه، بدون پرداخت

2026-10-22 · نسخه0.9.0 · شاخه arena/f6a09f64-webkiya. [نقشهٔ کامل۲۶](26-delivery-map.md) و `/progress` به‌روزند. F01..F16 حفظ شده؛ این تحویل هستهٔ اولیهٔ stage07/08 و F03/F04 است، نه تکمیل commerce یا FULL.

## مسیر مشتری و حدود

کالای واقعی در سبد سروری ← محاسبهٔ تازه ← تأیید صریح جمع و اقلام ← ثبت سفارش اولیه و رزرو موجودی. سفارش در همان `/basket` قابل مشاهده، reload و لغو است. تکی/عمده مستقل‌اند؛ سفارش عمده از یک جین با BOM واقعی شروع می‌شود. شماره/حساب آزمایشی مصنوعی برچسب دارد؛ live همچنان به تأیید واقعی شماره نیاز دارد و provider OTP وصل نیست. دادهٔ واقعی کسب‌وکار یا قیمت/موجودی حدسی ایجاد نشد.

رزرو حداکثر۱۲۰ثانیه از محاسبهٔ مجدد ثبت و محدود به انقضای price/partner است؛ اعتبار کمتر از۵ثانیه رد می‌شود. سقف سه رزرو فعال و۱۰درخواست ثبت در دقیقه برای هر حساب، حد فنی موقت است نه تصمیم تجاری، MOQ یا تضمین ضدسوءاستفاده. checkout واقعی، آدرس، مالیات، هزینهٔ ارسال، payable و تأیید نهایی فروش نداریم؛ paymentReady/fulfillmentReady=false. هیچ تراکنش مالی یا ارسال واقعی انجام نمی‌شود.

## قرارداد و تراکنش

- `POST /api/orders`: mode/version/fingerprint/requestId؛ مبلغ، userId یا status ورودی پذیرفته نمی‌شود. نشست مشتری فعال و شماره معتبر لازم است. fingerprint از محاسبهٔ سروری می‌آید و فقط اقلام/قیمت/نسخهٔ پذیرفته‌شده را مقایسه می‌کند؛ authorization ذخیره‌شده یا token امضاشده نیست. تغییر قیمت/نسخه حتی با موجودی کافی مستلزم محاسبه و تأیید مجدد است.
- calculateCart در transaction همان ثبت با lock سبد، محصول‌های مرتب، همکار و SKUهای مرتب اجرا می‌شود؛ phone/session، وضعیت محصول/جین، تخصیص قیمت معتبر همان همکار، BOM و stock-reserved تجمیعی دوباره بررسی می‌شوند. سپس snapshot پایدار، OrderHold و ledger ثبت، reserved و version زیاد و فقط همان سبد خالی و version آن زیاد می‌شود؛ audit در همان commit است. stock فیزیکی تغییر نمی‌کند.
- requestId/digest با advisory lock، درخواست تکراری را به همان سفارش برمی‌گرداند؛ payload متفاوت409. قفل هر مشتری برای سقف فعال و cartVersion یکتا برای جلوگیری از سفارش دوم همان نسخه برقرار است. در رقابت موجودی تنها سفارش دارای ظرفیت commit می‌شود؛ خطای بازنده سبد/stock/ledger را ناقص نمی‌گذارد.
- `GET /api/orders` پنجاه مورد اخیر همان مشتری با snapshot تاریخی است؛ قیمت جاری عمومی/همکار از این endpoint خوانده نمی‌شود. تعلیق همکاری، خواندن سوابق متعلق به خود مشتریِ دارای نشست معتبر را حذف نمی‌کند، ولی ثبت جدید دوباره تأیید همکار می‌خواهد. صفحه‌بندی کامل/جزئیات مستقل هنوز نیست.
- `POST /api/orders/:id/cancel` با version و Origin و مالکیت؛ فقط RESERVED به CANCELLED یا در صورت پایان مهلت به EXPIRED می‌رود. تکرار لغو همان وضعیت را برمی‌گرداند و دوباره آزاد نمی‌کند. شناسهٔ حساب دیگر404 است.
- PurchaseOrder از تغییر snapshot/هویت/قیمت و حذف محافظت شده؛ OrderHold و ReservationMovement append-only‌اند. migration011 در commit تطبیق hold با RESERVE/RELEASE و جلوگیری از کم‌کردن reserved به زیر hold فعال را بررسی می‌کند. این حفاظت‌ها جای runtime کم‌اختیار یا ممیزی مستقل نیستند؛ ماندهٔ رزروهای خارج از دفتر قدیمی به‌طور خودکار بازنویسی نمی‌شود.

## انقضا و عملیات

`kiya_release_order` یک primitive SQL مشترک HTTP/CLI/worker است: lock سفارش سپس SKU مرتب، کاهش reserved، افزایش version، ledger RELEASE و audit اتمیک. دو worker یا لغو/انقضای هم‌زمان، یک بار آزاد می‌کنند. هر سفارش در transaction جدا آزاد می‌شود تا قفل SKU چند سفارش با هم انباشته نشود.

`npm run worker:reservations` هر۱۰ثانیه حداکثر۱۰۰مورد منقضی را بررسی می‌کند، توقف SIGINT/SIGTERM را می‌پذیرد و شناسه/قیمت/اطلاعات مشتری log نمی‌کند. `--once` برای اجرای یک batch از فایل اسکریپت قابل استفاده است. `db:maintenance` یک batch آزادسازی و پاک‌سازی rate/session دارد. ثبت سفارش نیز حداکثر۵۰مورد عمومی منقضی و تاریخچه حداکثر۵۰مورد متعلق به همان مشتری را آزاد می‌کند. صرف عبور ساعت بدون worker/درخواست مقدار DB را عوض نمی‌کند؛ در backlog ممکن است چند batch لازم باشد. supervisor، health/alert، backoff/reconnect و SLA تولید هنوز پیاده/تأیید نشده‌اند؛ اگر اتصال DB worker قطع شد باید supervisor آن را بازیابی کند. کنترل پرداخت آینده باید expiry/status/partner/price را مستقل دوباره بررسی کند و به تأخیر worker تکیه نکند.

## فایل‌ها و آزمون‌ها

migration010/011 و schema؛ `src/server/cart.ts` (استخراج calculateCart مشترک و fingerprint و شناسهٔ اجزا)، `src/server/orders.ts`، APIهای orders و cancel؛ `server-basket.tsx` و `order-history.tsx` و CSS؛ worker و maintenance، تست backend/e2e، ADR019 و نقشهٔ تحویل. migrationهای اعمال‌شدهٔ قبلی تغییر نکرده‌اند؛ dev/test مهاجرت شدند.

۹۷ تست PostgreSQL شامل۱۶مورد جدید: snapshot/رزرو، retry موازی، کلید متفاوت روی یک cartVersion، رقابت دو مشتری، احراز/Origin/قیمت تزریقی/مالکیت، تغییر قیمت و اعتبار همکار/offer، یک جین با مقدار واقعی، لغو/انقضا و رقابت آن‌ها، محافظ موجودی رزروشده، consistency در commit، سقف فعال و CLI maintenance. تست expiry تنها در DB تست ایزوله تاریخ fixture را با خاموش‌کردن موقت یک guard و فعال‌سازی مجدد آن تغییر می‌دهد؛ API یا worker چنین قابلیتی ندارد. E2E چرخهٔ ثبت، reload، نمایش snapshot، لغو و reserved صفر را روی build production اجرا می‌کند. cleanup جدول‌های سفارش/hold/ledger فقط مشتری/محصول مصنوعی همان تست است؛ dev truncate نمی‌شود و مالک واقعی/MFA تغییر نمی‌کند.

## مرحلهٔ بعد و وابستگی‌ها

مدیریت سفارش با RBAC و scope، تاریخچهٔ کامل، آدرس و مدل سیاست ارسال/مالیات، سپس adapter sandbox پرداخت و snapshot مالی کامل، verify/idempotency/reconciliation و تبدیل رزرو به فروش. تمدید رزرو، retry/outbox و اعلان، لغو/refund پس از پرداخت، هزینه/سود، حقوقی و قواعد کالا، آزمون بار، production worker/backup و ممیزی بازند. مبلغ و سیاست ارسال/مالیات واقعی، کلید provider، DNS و دادهٔ فروشگاه نباید حدس زده شوند. noindex و خاموش‌بودن پرداخت باقی است.

اعتبارسنجی نهایی: ۹۷backend،۱۲unit،۱۰E2E production (از جمله عرض‌های360/390/768/1440 در تاریخچهٔ سفارش)،۱۱Python، lint/typecheck/build، Prisma validate، validator اسناد، diff check و audit وابستگی‌های runtime با صفر آسیب‌پذیری گزارش‌شده موفق بودند. worker --once با موفقیت اجرا شد و worker دوره‌ای در پیش‌نمایش محلی فعال است؛ استقرار تولید انجام نشده است. این نتایج جای ممیزی مستقل یا پذیرش نهایی مالک نیستند.
