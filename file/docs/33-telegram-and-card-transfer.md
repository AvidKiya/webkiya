# ۳۳ — ورود مشتری با تلگرام و پرداخت کارت‌به‌کارت

2026-10-23 · پیاده‌سازی در `kiya-site/` · شاخه `arena/2c244362-webkiya`

این سند وضعیت اجرایی درخواست جدید مالک است، نه اعلام تکمیل همهٔ F01..F16 یا راه‌اندازی تولید. متن وضعیت توسعه، لینک **نمایان** پرش و شرح بلند هدر از فروشگاه منتخب حذف شدند؛ نسخهٔ ۳۶فایلی `template-original` دست‌نخورده است. skip link صفحه‌های بک‌اند از قبل فقط هنگام فوکوس کیبورد دیده می‌شود.

## ورود موقت به‌جای SMS

- حساب من ← «ورود با حساب تلگرام» ← دریافت لینک یک‌بارمصرف ← بازکردن بات ← مقایسهٔ کد شش‌رقمی با همین مرورگر ← تأیید خصوصی در بات ← تأیید صریح هویت در همان مرورگر.
- اعتبار درخواست **۳ دقیقه** است. selector تصادفی و proof مرورگر مستقل‌اند؛ proof در کوکی HttpOnly با مسیر محدود و SameSite است. دیتابیس فقط hash آن دو را نگه می‌دارد. کد نمایشی به‌تنهایی رمز ورود نیست.
- Telegram numeric ID از update معتبر با secret مستقل، گفت‌وگوی private و تطابق sender/chat می‌آید. update_id تکراری اثری ندارد. شناسه/نام کاربری دلخواه فرستاده‌شده توسط مرورگر معتبر نیست.
- حساب جدید فقط CUSTOMER است، بدون نقش مدیریت یا شمارهٔ تأییدشدهٔ ساختگی. ورود مجدد همان numeric ID همان حساب را پیدا می‌کند؛ ادغام با حساب شماره‌تلفنی/آزمایشی یا کارکنان خودکار نیست. بررسی همکاری همچنان مستقل و مجوزدار است.
- این مسیر **Mini App/initData، SMS OTP، فرمان مدیریت داخل بات، منوی کامل ربات یا انتشار کانال نیست**. وضعیت تکمیل بقیهٔ F09 تغییر نکرده است.

## تنظیم امن و فعال‌سازی واقعی

۱. migrationها را اجرا کنید: `npm --prefix backend run db:migrate`، سپس seed نقش‌ها `npm --prefix backend run db:seed`. migrationهای 012 تا016 اضافه شده‌اند؛ migration اعمال‌شده را ویرایش نکنید.
۲. حساب OWNER واقعی و MFA لازم است: راهنمای [۲۴](24-real-owner-and-access.md) و `backend/scripts/create-owner.mjs`. رمز یا کلید را در چت، Git، URL عمومی یا لاگ نگذارید. در دیتابیس توسعهٔ بازیابی‌شده، حساب مالک قبلی بازیابی نشده است؛ fixture آزمون مالک واقعی نیست.
۳. پس از ورود کارکنان و MFA، `/admin/settings`: نام `kiyaco24bot`، توکن **تازهٔ ابطال‌نشده** و webhook secret مستقل حداقل۳۲کاراکتری، سپس ذخیره. توکن قبلاً افشاشده باید در BotFather revoke شود؛ این کد آن را استفاده/بازتولید نمی‌کند.
۴. توکن/secret با AES-256-GCM و `MFA_ENCRYPTION_KEY` مشترک وب و worker در دیتابیس رمز می‌شوند. read API فقط configured flags برمی‌گرداند، نه secret. ورودی خالی secret قبلی را نگه می‌دارد؛ خاموش‌کردن اتصال از checkbox انجام می‌شود. نسخه و audit مانع ذخیرهٔ قدیمی/نشت secret هستند. fallback اختیاری `TELEGRAM_BOT_TOKEN` و `TELEGRAM_WEBHOOK_SECRET` فقط env سمت سرور است.
۵. «آزمون اتصال واقعی ربات» درخواست `getMe` می‌زند و username را تطبیق می‌دهد. ذخیرهٔ تنظیمات ≠ اتصال سالم. موفقیت getMe نیز به‌تنهایی تحویل پیام یا ورود انتهابه‌انتها را ثابت نمی‌کند.
۶. **یکی** از دو روش دریافت:
   - webhook: در میزبان `NEXT_PUBLIC_SITE_URL=https://kiyaco24.ir` و مسیر `/api/webhooks/telegram` روی HTTPS عمومی؛ دکمهٔ ثبت webhook در تنظیمات. `npm run worker:telegram` در پوشهٔ backend برای ارسال outbox همچنان لازم است.
   - polling: دکمهٔ «استفاده از polling» webhook را بدون حذف پیام‌های معلق پاک می‌کند؛ در backend اجرا کنید: `npm run worker:telegram:poll`. این گزینه به webhook عمومی احتیاج ندارد، ولی مرورگر باید به سایت و میزبان به API تلگرام دسترسی داشته باشد.
۷. worker روی همان میزبان Node22 و همان DB/key وب اجرا می‌شود. `TELEGRAM_INTERNAL_ORIGIN` پیش‌فرض `http://127.0.0.1:3101` است و فقط loopback HTTP قبول می‌شود؛ این آدرس داخلیِ worker است، نه URL مرورگر. اگر پورت بک‌اند فرق دارد آن را تغییر دهید. process manager با restart و graceful shutdown حداقل۴۰ثانیه لازم است؛ فقط یک worker به‌کمک advisory lock مجاز است.
۸. با حساب تست مالک، کل زنجیرهٔ شروع/تأیید در تلگرام/تأیید مرورگر/خروج/ورود مجدد را **در ارائه‌دهندهٔ واقعی** تست کنید. بعد اعلام فعال‌بودن کنید. در این تحویل توکن تازه در دسترس نبود و هیچ تماس واقعی با تلگرام انجام نشد.

outbox در DB پایدار است. در قطع مبهم شبکه نتیجه `UNKNOWN` می‌شود و ارسال کور تکرار نمی‌شود؛ کاربر لینک تازه می‌گیرد. 429 با retry_after رعایت می‌شود. پیام ورودِ بیش از۳دقیقه ارسال نمی‌شود. دادهٔ challenge و outbox نهایی پس از یک روز و dedup پس از۶روز پاک می‌شوند؛ بازهٔ dedup از نگهداری update در Telegram بلندتر است و مانع مشکل offset تصادفی بعد از یک هفته سکوت می‌شود. payload بزرگ/ناسازگار در polling بدون گیرکردن صف رد می‌شود؛ خاموش‌کردن اتصال مانع شروع/اتمام ورود تازه می‌شود.

**استقرار Cloudflare قبلی فقط آماده‌سازی بود.** worker طولانی‌عمر Node به‌صرف build OpenNext روی Workers اجرا نمی‌شود؛ برای آن میزبان Node مجزا/سازگار یا آداپتور job لازم است. این تغییر ادعای deploy دامنه یا اجرای دائمی worker ندارد.

## کارت‌به‌کارت موقت

- OWNER در همان تنظیمات بانک، صاحب کارت، شمارهٔ کارت با کنترل طول/Luhn، هزینهٔ ثابت ارسال، مالیات مبلغ ثابت به **تومان** و مهلت۱۵تا۱۴۴۰دقیقه را ثبت می‌کند. اعتبارسنجی شمارهٔ کارت احراز مالکیت حساب بانک نیست. نرخ مالیات خودکار یا قرارداد حمل‌ونقل از این اعداد استنباط نشود.
- سبد/quote و رزرو همان منبع سروری قبلی‌اند. از «حساب من» روی رزرو معتبر، گیرنده/تماس/شهر/نشانی/کدپستی را وارد کنید؛ سرور مبلغ کالا + ارسال + مالیات و مقصد/نشانی را snapshot می‌کند. amount ورودی مشتری پذیرفته نمی‌شود. ایجاد intent دوباره، پرداخت یا تمدید تازه نمی‌سازد.
- تنها ایجاد intent، مهلت hold را یک بار با تنظیم مدیر تمدید می‌کند؛ سفارش‌های رهاشده همچنان به اجرای دوره‌ای `db:maintenance` نیاز دارند. ساعت انقضا را رعایت کنید، بعد از انقضا واریز نکنید.
- رسید تصویری واقعی و کد پیگیری بارگذاری می‌شود؛ حداکثر فایل۵MB، بدنه۶MB، JPEG/PNG/WebP معتبر، normalize WebP و hash سمت سرور. **عکس کارت، رمز، CVV2 یا OTP نفرستید.** فایل private است و فقط صاحب پرداخت یا کارمند دارای `payment:review` و MFA می‌تواند از API no-store بخواند؛ خواندن مالی audit می‌شود. URL عمومی محصول برای رسید ساخته نمی‌شود.
- `AWAITING_TRANSFER → UNDER_REVIEW`. بارگذاری تصویر پرداخت را تأیید نمی‌کند. `/admin/payments` برای نقش مالی محدود نیز کار می‌کند؛ این نقش به `/admin/settings` یا secret ربات دسترسی ندارد.
- کارمند مجاز باید **گردش واقعی بانک، مبلغ و حساب مقصد را مستقل از تصویر** تطبیق دهد؛ تیک صریح، دلیل حداقل۱۰کاراکتری و **شناسهٔ یکتای ردیف گردش بانک از خود بانک** ضروری‌اند. اگر بانک شناسه را بین روزها تکرار می‌کند، تاریخ/شناسهٔ کامل گردش را وارد کنید، نه صرفاً کد ادعاشدهٔ مشتری. مقصد ثابت هر پرداخت در صفحهٔ مالی نمایش داده می‌شود. کلید مقصد+شناسهٔ تطبیق‌شده در DB یکتا است؛ حتی تصویر متفاوت نمی‌تواند همان واریز را برای دو سفارش مصرف کند. این کنترل جای تطبیق انسانی را نمی‌گیرد. برای رکوردهای تاریخی احتمالیِ قبل از migration016 شناسهٔ بانک جعل/backfill نمی‌شود؛ آن‌ها به ممیزی مستقل نیاز دارند. رد رسید با دلیل امکان اصلاح می‌دهد. یک تصویر واحد بین پرداخت‌ها پذیرفته نمی‌شود؛ این جایگزین تشخیص تقلب یا استعلام بانک نیست.
- تأیید معتبر: snapshot پرداخت CONFIRMED + سفارش PAID + کسر stock + آزادکردن reserved + دفتر موجودی و audit، همه در **یک تراکنش**، با قفل و تازه‌سنجی مجوز. تکرار/رقابت تأیید، فروش دوم نمی‌سازد. constraint و ledger پیوندخورده به UUID سفارش از ناسازگاری جلوگیری می‌کنند.
- واریز تطبیق‌شده بعد از انقضا/لغو: `REFUND_REQUIRED` تغییرناپذیر، بدون PAID/کسر موجودی؛ ارسال نکنید و استرداد واقعی را خارج از سامانه پیگیری/مستند کنید. **پردازش خودکار refund، تسویهٔ بانکی، gateway، لیبل/رهگیری حمل و مرجوعی کامل پیاده نشده‌اند.**
- DTO قدیمی رزرو همچنان payableToman=null/paymentReady=false دارد چون خودش payment intent نیست؛ مبلغ و آمادگی کارت‌به‌کارت از `/api/payments?orderId=...` خوانده می‌شوند. UI جدید از همین مسیر استفاده می‌کند.

رسانهٔ private باید روی volume ماندگار با دسترسی محدود و بکاپ امن باشد. عمر قانونی نگهداری رسید/نشانی و حذف orphanهای قدیمی باید پیش از تولید تعیین شود؛ حذف فوری فایلِ یک تراکنش ناموفق، با upload هم‌زمان امن نیست. هیچ اطلاعات بانکی/هویتی fixture به production منتقل نشود.

## شواهد محلی

- ۱۱۳ تست PostgreSQL/API (شامل دسترسی owner/MFA، encryption/version/audit، جعل/تکرار/انقضای تلگرام، مرورگر دیگر، مصرف هم‌زمان، هویت مشتری و gate همکاری؛ مبلغ/نشانی ثابت، مالکیت رسید، role مالی و ابطال نشست، capture یک‌بار، جلوگیری از مصرف دوبارهٔ ردیف بانک با تصویر متفاوت، انقضا و refund-required).
- ۲۳ تست واحد backend/frontend؛ typecheck هر دو پروژه و build مستقل.
- مرورگر واقعی: لینک و تأیید تلگرام با **update مصنوعی روی webhook محلی**، خرید از خود پست/سبد، رزرو، نشانی/مبلغ سرور، رسید خصوصی و reload، بررسی با **نقش سفارشی مالی محدود**، تأیید/PAID، خروج و عدم دسترسی، موبایل بدون overflow و خطای JS. تطبیق بانک نیز صرفاً دادهٔ مصنوعی تست است، نه پول واقعی.
- تست مرورگری عمدهٔ قبلی و hash تمام۳۶فایل قالب محفوظ‌اند. تست API واقعی Telegram با mock transport برای adapter، getMe mismatch/failure و set/deleteWebhook پوشش داده شد؛ mock ≠ provider سالم.

بازتولید از `kiya-site/`:
```sh
npm run test:wholesale:prepare
npm run dev:ui-test
# در ترمینال دیگر، روی DB کاملاً مجزای kiya_test:
npm run test:telegram-payment:browser
npm run test:wholesale:browser
# سرویس آزمون را قبل از build متوقف کنید
npm run test:unit
npm run test:template
npm run build
```
آماده‌سازی فقط با guard دیتابیس محلی `kiya_test` انجام می‌شود و fixture کوکی‌ها زیر `.data` نادیده‌گرفته‌شده است؛ آن را پس از آزمون پاک کنید. هیچ رمز واقعی، bot token واقعی، کارت واقعی، نشست واقعی یا فایل .env به Git اضافه نشده است.
