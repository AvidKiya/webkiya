# ۳۴ — مدیریت روی همان حساب کاربری، بدون یوزر/رمز جدا

2026-10-24 · `kiya-site/` · درخواست جدید مالک، جایگزین UX ورود پرسنلی سند۳۳/۲۴.

- نوار بنفش KIYA/«ورود به مدیریت امن» و دکمهٔ عمومی هدر حذف شدند؛ نشان اصلی برند حذف نشده است.
- ورود عادی مشتری و مدیر از «حساب من» و همان تلگرام انجام می‌شود. دکمهٔ «پنل مدیریت» تنها وقتی metadata سروری adminAccess را تأیید کند داخل حساب دیده می‌شود؛ داشتن لینک یا تغییر state مرورگر هیچ مجوزی نیست.
- شناسهٔ حساب، Telegram ID، سفارش‌ها، رسیدها و همکاریِ همان حساب حفظ می‌شوند. پس از مدیرشدن، خرید و دسترسی فقط به سفارش‌های خود نیز حفظ می‌شود؛ نقش مدیریتی جای تأیید همکاری/قیمت خصوصی نیست.
- پنل `/admin` دیگر فرم نام کاربری/رمز ندارد؛ نشست مدیرِ واردشده با تلگرام ابتدا MFA را تکمیل می‌کند. عملیات مدیریت هنوز سمت سرور هم نقش و هم MFA را بررسی می‌کنند؛ تأیید تلگرام به‌تنهایی MFA مدیر محسوب نمی‌شود. APIهای قدیمی رمز صرفاً برای سازگاری/بازیابی اپراتوری باقی‌اند و مسیر عادی UI نیستند. حساب جدید مدیر نه passwordHash می‌گیرد و نه handle ساختگی.

## تأیید شماره و مالک اولیه

شماره‌ای که مالک اعلام کرده فقط در env خصوصی و نادیده‌گرفته‌شدهٔ این محیط به‌عنوان `KIYA_BOOTSTRAP_OWNER_PHONE` ثبت شده؛ مقدار شخصی در Git/این سند نیست. **هیچ حساب یا نشست واقعی هنوز با آن شماره احراز نشده است.**

۱. ابتدا توکن **جدید** بات و secret مستقل از مسیر امن میزبان وارد شوند؛ توکن افشاشدهٔ قبلی استفاده نشود. برای نصب اول که OWNER هنوز وجود ندارد، اپراتور مورد اعتماد می‌تواند فقط در env سرور `TELEGRAM_BOT_TOKEN`، `TELEGRAM_WEBHOOK_SECRET` و `TELEGRAM_LOGIN_ENABLED=true` را تنظیم کند. اگر StoreSettings وجود دارد، مقدار صریح telegramEnabled آن بر env اولویت دارد. وب و worker باید همان DB/key و env به‌روز را داشته باشند. secrets به چت/فرانت‌اند/Git نروند.
برای نصب اول، قبل از worker، `npm run telegram:first-install:poll` یا `npm run telegram:first-install:webhook` در backend اجرا شود؛ getMe واقعی و روش دریافت را بدون چاپ token تنظیم می‌کند، webhook قدیمیِ polling را بدون حذف updateهای معلق پاک می‌کند و اگر StoreSettings موجود باشد از این ابزار اولیه استفاده نمی‌کند. در نصب موجود از تنظیمات OWNER/MFA استفاده کنید. این ابزار در تحویل بدون کلید واقعی اجرا/متصل اعلام نشده است.

۲. مقدار `KIYA_BOOTSTRAP_OWNER_PHONE` فقط در تنظیم خصوصی میزبان، توسط اپراتور مجاز تعیین شود؛ این متغیر از HTTP قابل تنظیم نیست و نباید از input ناشناس گرفته شود.
۳. کاربر لینک کوتاه‌عمر سایت را در بات باز و تأیید می‌کند. سپس با دکمهٔ native «اشتراک شمارهٔ خودم» شماره را می‌فرستد. پیام متنی شماره، کارت تماس فرد دیگر، گروه یا from/chat ناسازگار پذیرفته نیست. contact.user_id باید دقیقاً sender همان گفت‌وگوی خصوصی معتبر باشد؛ secret webhook و dedup همچنان لازم‌اند.
۴. یک challenge تأییدشدهٔ همان Telegram ID باید هنوز در مهلت۳دقیقه باشد. phone فقط از contact معتبر در آن ذخیره می‌شود. شماره‌ای که به حساب دیگری متصل است خودکار merge یا به مدیر قدیمی attach نمی‌شود.
۵. تنها اگر شمارهٔ احرازشده با env خصوصی مالک برابر باشد و **هیچ OWNER موجودی، حتی غیرفعال، نباشد**، نقش OWNER در تراکنش و با قفل مشترک ابزار bootstrap قدیمی داده می‌شود. داشتن شماره یا Telegram ID دلخواه در درخواست مرورگر کافی نیست.
۶. اگر تماس بعد از اتمام ورود ارسال شود، ارتقای مالک نشست‌های قبلی را باطل می‌کند؛ کاربر با لینک تازه به **همان شناسهٔ حساب** وارد می‌شود. اگر تماس پیش از اتمام ورود برسد، همان ورود با نقش صحیح ولی MFA-pending تمام می‌شود.
۷. سپس دکمهٔ پنل و ثبت/تأیید Authenticator. MFA و کدهای بازیابی صرفاً برای صاحب حساب‌اند. بعد از راه‌اندازی مالک، اپراتور env bootstrap را پاک کند. این مکانیزم تعویض مالک یا دورزدن تعلیق مالک قبلی نیست.

ربات پس از تأیید لینک، درخواست native تماس را در outbox می‌گذارد؛ worker باید نسخهٔ جدید و migration017 را داشته باشد. اشتراک شماره برای خرید معمولی اختیاری است، اما معرفی حساب به مدیریت نیاز به تلگرام **و شمارهٔ احرازشده** دارد. این احراز شماره از تلگرام است، نه ادعای ارسال SMS.

## مدیران دیگر و سطح‌بندی

مالکِ دارای MFA ← پنل ← تیم و دسترسی‌ها ← «مدیر کردن حساب کاربری تأییدشده»:
- انتخاب همان کاربر با نام، شمارهٔ ماسک‌شده و UUID؛ فقط حساب واقعیِ فعال با Telegram/phone verification وارد فهرست می‌شود.
- تعیین نقش پایه یا سفارشی، دلیل حداقل۱۰نویسه؛ نقش OWNER نیاز به تأیید صریح اختیارات کامل دارد.
- `POST /api/admin/staff/promote` فقط OWNER+MFA، با reauthorization داخل تراکنش، قفل نقش/کاربر، audit و ابطال نشست‌های قبلی. مشتری، پشتیبان و دارندهٔ session قدیمی حق ارتقای خود ندارند.
- کاربر دوباره از همان تلگرام وارد می‌شود؛ دکمهٔ پنل ظاهر می‌شود و MFA را تکمیل می‌کند. تغییر نقش/تعلیق بعدی نیز نشست‌ها را باطل می‌کند؛ قاعدهٔ آخرین مالک و منع ویرایش نقش خود همچنان برقرار است.

نام یا نقش ارسالی از فرانت‌اند منبع مجوز نیست. bootstrap تلفنیِ امن فقط اولین مالک را می‌سازد؛ شمارهٔ هر مدیر دیگر به‌تنهایی نقش نمی‌دهد. لینک عمومی `/admin` مخفی‌کردن امنیتی محسوب نمی‌شود و endpointها همچنان 401/403 می‌دهند.

## شواهد و مرز ادعا

- ۱۱۶ تست PostgreSQL/API: تماس شخص دیگر رد، شمارهٔ معتبر بدون اعطای خودکار مالک در حضور مالک قبلی، bootstrap هدف با اثبات تماس، ابطال نشست، همان ID، عدم password/handle، MFA، تداوم سفارش و خرید بعد از اعطای نقش؛ تست‌های پرداخت/عمدهٔ قبل نیز سبز.
- مرورگر `npm run test:account:browser`: نبود نوار/دکمهٔ عمومی؛ ورود مشتری و own-contact؛ اعطای SUPPORT از خود UI مالک؛ ابطال نشست؛ ورود دوباره با همان ID؛ دکمهٔ حساب؛ نبود فرم password؛ ثبت MFA و scope محدود، خرید/خروج/موبایل.
- آزمون‌های مرورگر پرداخت و عمده نیز تکرار شدند. provider و تماس این آزمون‌ها مصنوعی و فقط روی kiya_test هستند؛ نه احراز واقعی شمارهٔ مالک یا تماس با Telegram API.
- migration017 فیلد تماس/keyboard، migration018 هویت Telegram را مستقل از CUSTOMER/STAFF می‌کند. migrationهای اعمال‌شده ویرایش نشده‌اند.

برای بازتولید از `kiya-site/`، ابتدا `npm run test:wholesale:prepare`، سپس `npm run dev:ui-test` و در ترمینال دیگر `npm run test:account:browser`. fixture صرفاً .data خصوصی/ignored است و پس از آزمون حذف شود. وب/worker پس از تغییر env نیاز به restart دارند. اتصال واقعی همچنان به توکن تازه و شبکهٔ میزبان و آزمون واقعی با خود مالک نیاز دارد؛ ذخیرهٔ شماره، مجوز یا healthy بودن bot نیست.
