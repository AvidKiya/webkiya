# ۳۴ — حساب یکپارچه و دو روش ورود تلگرام

2026-10-24 · `kiya-site/` · جایگزین UX ورود جداگانهٔ پرسنلی سند۳۳/۲۴.

## دو روش در «حساب من»

- **ورود مستقیم با ربات:** دکمهٔ سایت یک لینک یک‌بارمصرف، کوتاه‌عمر و مقید به مرورگر ایجاد و Telegram را باز می‌کند. زدن **Start** در گفت‌وگوی خصوصی همان درخواست را تأیید می‌کند؛ مرورگر اولیه با polling و هنگام بازگشت خودکار وارد می‌شود. کلیک تأیید دیگری در ربات یا سایت لازم نیست. اگر popup مسدود باشد، لینک جایگزین نمایش داده می‌شود. انتقال لینک به مرورگر دیگر اجازهٔ ساخت نشست در مرورگر دوم نمی‌دهد. callback قدیمی فقط برای سازگاری درخواست‌های قدیمی باقی است، نه مسیر UI جدید.
- **کد تلگرام:** شمارهٔ قبلاً تأییدشده وارد سایت می‌شود و کد۶رقمی به گفت‌وگوی Telegram همان حساب می‌رود؛ کد در سایت وارد می‌شود. کد۳دقیقه معتبر، به مرورگر درخواست‌کننده مقید، یک‌بارمصرف و دارای حداکثر۵تلاش پایدار است. ارقام فارسی پذیرفته می‌شوند. محدودیت درخواست روی مرورگر، شماره و IP وجود دارد. پاسخ شمارهٔ ناشناس عمومی است؛ کد عمومی یا OTP نمایشی وجود ندارد.
- ربات نمی‌تواند به کاربری که هرگز Start نزده پیام خصوصی آغاز کند. برای راه‌اندازی اولیهٔ OTP، کاربر یک‌بار بات را Start می‌کند و از دکمهٔ native «اشتراک شمارهٔ خودم» شماره می‌فرستد. متن شماره، تماس فرد دیگر، گروه و contact.user_id ناسازگار پذیرفته نیستند. ثبت شماره بعد از ورود مستقیم هم ممکن است؛ برای ثبت اولیه نیاز به ورود پنل مدیریت نیست.
- هر دو روش همان Telegram ID و همان حساب را استفاده می‌کنند. کد فقط به حساب فعال، غیرنمایشی و دارای شمارهٔ native تأییدشده ارسال می‌شود. digest با HMAC و secret سرور ذخیره می‌شود؛ متن منتظر ارسال در outbox با AES-GCM رمزگذاری شده و فقط worker آن را رمزگشایی می‌کند. مصرف کد/لینک با تراکنش و قفل از replay و مصرف هم‌زمان جلوگیری می‌کند.

## راه‌اندازی ربات، مستقل از ورود مدیر

اپراتور مورد اعتماد در env خصوصی سرور `TELEGRAM_BOT_TOKEN`، `TELEGRAM_WEBHOOK_SECRET` مستقل و `TELEGRAM_LOGIN_ENABLED=true` را تنظیم می‌کند. StoreSettings موجود و مقدار صریح telegramEnabled بر env اولویت دارند. وب و worker باید DB، کلید رمزنگاری و env یکسان داشته باشند؛ بعد از تغییر env هر دو restart شوند. secrets نباید به فرانت‌اند، Git یا لاگ بروند. توکن منتشرشده در چت باید تعویض شود؛ توکن جایگزین فقط در میزبان وارد شود.

در backend، برای نصب اول `npm run telegram:first-install:poll` یا `npm run telegram:first-install:webhook` اجرا می‌شود. این ابزار نیازی به نشست مدیر ندارد، ولی روی StoreSettings موجود اجرا نمی‌شود. worker با `npm run worker:telegram:poll` جدا از لاگین اجرا می‌شود؛ نبود StoreSettings مانع خواندن env نیست. پیش از دریافت/ارسال، `getMe` و تطبیق username را انجام می‌دهد؛ در polling، webhook قبلی را با `drop_pending_updates:false` حذف می‌کند. برای webhook فقط `npm run worker:telegram` اجرا می‌شود. worker با قفل DB از اجرای هم‌زمان دو transport جلوگیری می‌کند. موفقیت process یا build به‌تنهایی اثبات اتصال Telegram نیست.

**وضعیت واقعی این محیط:** تنظیم خصوصی و ابزار نصب مستقل امتحان شدند؛ درخواست واقعی `getMe` پیش از پاسخ HTTP با `ECONNRESET` شکست خورد. اعتبار توکن و هویت بات از provider تأیید نشده، پیام واقعی یا ورود مالک انجام نشده و deployment تولیدی ادعا نمی‌شود. محدودیت شبکهٔ میزبان باید رفع و سپس getMe، دریافت Start و ارسال OTP با Telegram واقعی آزموده شوند. خطا نباید با پاسخ جعلی provider یا غیرفعال‌کردن احراز پوشانده شود.

## همان حساب برای خرید و مدیریت

- نوار عمومی KIYA/ورود مدیریت حذف شده؛ لوگوی برند باقی است. دکمهٔ پنل فقط براساس adminAccess سرور در حساب مجاز ظاهر می‌شود. مخفی‌بودن لینک جای authorization نیست؛ endpointها همچنان 401/403 می‌دهند.
- حساب، Telegram ID، سفارش‌ها، رسیدها و خرید کاربر بعد از مدیرشدن حفظ می‌شوند؛ نقش مدیریتی جای تأیید همکاری/قیمت خصوصی نیست.
- پنل فرم نام کاربری/رمز جدا ندارد. مدیر پس از ورود تلگرام MFA را تکمیل می‌کند؛ تمام عملیات مدیریت همچنان نقش و MFA می‌خواهند. API قدیمی رمز صرفاً سازگاری/بازیابی اپراتوری است. حساب جدید handle یا password ساختگی ندارد.

## مالک اولیه و مدیران محدود

`KIYA_BOOTSTRAP_OWNER_PHONES` فهرست خصوصی حداکثر۱۰شمارهٔ مجاز است و بر متغیر قدیمی تک‌شماره‌ای `KIYA_BOOTSTRAP_OWNER_PHONE` اولویت دارد. `KIYA_BOOTSTRAP_OWNER_TELEGRAM_ID` شناسهٔ عددی مورد انتظار را محدود می‌کند: در این نصب **یکی از دو شمارهٔ مجاز و همان شناسه** باید با contact معتبر اثبات شوند. مقدار شخصی در Git/این سند نیست؛ تنظیم نامعتبر fail-closed است. شماره یا ID نوشته‌شده در مرورگر اثبات نیست.

اعطای مالک تنها با تماس معتبر Telegram، حساب مجاز و نبود **هرگونه OWNER حتی غیرفعال** در تراکنش و قفل مشترک bootstrap انجام می‌شود. شمارهٔ حساب دیگر خودکار merge نمی‌شود. ارتقای پس از اتمام ورود نشست قبلی را باطل می‌کند؛ ورود دوباره به همان حساب و MFA لازم است. بعد از راه‌اندازی، اپراتور متغیر bootstrap را پاک می‌کند. این سازوکار تعویض مالک یا دورزدن تعلیق نیست.

مالک دارای MFA از «تیم و دسترسی‌ها» همان مشتری Telegram/شماره‌تأییدشده را به نقش پایه یا سفارشی با scope محدود ارتقا می‌دهد. دلیل حداقل۱۰نویسه و برای OWNER تأیید صریح لازم است؛ audit، reauthorization و ابطال نشست اجرا می‌شوند. مشتری نمی‌تواند خود را ارتقا دهد؛ قاعدهٔ آخرین مالک و منع ویرایش نقش خود پابرجاست. نقش ارسالی فرانت‌اند منبع مجوز نیست.

## شواهد و بازتولید

- ۱۲۰ تست PostgreSQL/API: ورود مستقیم فقط با Start، محدودیت مرورگر، replay، ثبت تماس بدون challenge، OTP غلط/انقضا/۵تلاش/رقم فارسی، مصرف هم‌زمان، پاسخ عمومی شمارهٔ ناشناس؛ سیاست مالک، MFA، نقش و پرداخت نیز پوشش دارند.
- از `kiya-site/` ابتدا `npm run test:wholesale:prepare`، سپس `npm run dev:ui-test`؛ در ترمینال دیگر `npm run test:telegram-modes:browser`، `npm run test:account:browser` و `npm run test:telegram-payment:browser`. سه suite مرورگر پاس شده‌اند: دو روش، یکسان‌بودن شناسه، پنل مشروط، اعطای SUPPORT از UI مالک، MFA، پرداخت و موبایل.
- در backend، `npm run test:telegram:transport` اجرای واقعی process خود worker را روی kiya_test با HTTP provider شبیه‌سازی‌شده می‌آزماید: getMe، polling بدون حذف update، getUpdates، رمزگشایی outbox و ثبت SENT. این تست **هیچ پیام واقعی تلگرام** نمی‌فرستد.
- تمام هویت‌ها، تماس‌ها و پاسخ‌های provider آزمون مصنوعی‌اند و فقط kiya_test را هدف می‌گیرند. fixture و فایل‌های موقت خصوصی/ignored هستند. تست خودکار اثبات مالک واقعی نیست.
- migration017 تماس/keyboard، migration018 هویت مشترک CUSTOMER/STAFF و migration019 جدول OTP و direct autoApprove را اضافه می‌کنند؛ migrationهای اعمال‌شده ویرایش نشده‌اند.
