# ۳۶ — گفت‌وگوی خصوصی و صندوق پشتیبانی سروری

2026-10-24 · `arena/2c244362-webkiya` · ادامهٔ تکمیل سایت، بدون استقرار خارجی.

## مسیر مشتری و پشتیبان

در ویترین، «دایرکت و پشتیبانی» (`/#inbox`) دیگر ترد/پاسخ محلی نمایشی ندارد. مشتری واردشده درخواست با موضوع و متن می‌سازد؛ در صورت نیاز از بین سفارش‌های خودش یکی را مرتبط می‌کند. متن روی PostgreSQL ذخیره، پس از reload بازیابی و در همان گفت‌وگو پاسخ داده می‌شود. مشتری می‌تواند درخواست خود را ببندد یا دوباره باز کند. گفت‌وگوی بسته پیام عمومی جدید نمی‌پذیرد تا باز شود.

پنل مجاز ← «صندوق پشتیبانی خصوصی» (`/admin/support`): فهرست درخواست‌های باز/بسته، صفحه‌بندی۲۰تایی، پیام‌های قبلی و سفارش مرتبط. پاسخ عمومی با برچسب «پشتیبانی کیا» به همان مشتری نمایش داده می‌شود؛ اسم/شناسهٔ خصوصی کارمند منتشر نمی‌شود. ثبت پیام فقط ذخیره‌شدن در سایت است؛ read receipt، ارسال Telegram، اعلان بیرونی یا پاسخ خودکار ساختگی نداریم.

## مجوزهای جدا

- `support:read`: فهرست و خواندن مکاتبهٔ عمومی؛ نقش خواندنی فرم پاسخ یا تغییر وضعیت ندارد.
- `support:reply`: پاسخ عمومی؛ به‌علاوهٔ read لازم است.
- `support:note`: خواندن و نوشتن یادداشت داخلی؛ به‌علاوهٔ read لازم است. مجوز reply به‌تنهایی note را نشان نمی‌دهد. checkbox یادداشت داخلی صریح است؛ نقش فقط-note بدون reply نمی‌تواند پیام عمومی ارسال کند.
- `support:manage`: بستن/بازکردن درخواست با دلیل؛ به‌علاوهٔ read لازم است.

تمام مسیرهای کارکنان نشست معتبر، MFA و reauthorization داخل تراکنش می‌خواهند. این مجوزها فقط به OWNER در migration افزوده شده‌اند؛ سایر نقش‌ها از جمله SUPPORT قدیمی خودکار اختیار تازه نمی‌گیرند. مالک می‌تواند نقش سفارشی محدود را از ابزار موجود تیم/دسترسی تخصیص دهد. migration باعث افزایش permissionVersion مالک موجود و ورود مجدد او می‌شود، نه حذف MFA یا ساخت مالک تازه.

## حریم خصوصی و یکپارچگی

- هر GET/POST/PATCH مشتری با مالکیت ترد و وضعیت جاری حساب بررسی می‌شود. UUID گفت‌وگو یا سفارش، مجوز نیست؛ مشتری دیگر 404 می‌گیرد.
- note اصلاً وارد query عمومی پیام‌ها نمی‌شود. شناسهٔ note برای cursor مشتری نیز مثل شناسهٔ ناموجود رد می‌شود؛ query اضافی internal پذیرفته نیست. زمان فعالیت عمومی و version عمومی با note تغییر نمی‌کنند، پس یادداشت از این metadata هم لو نمی‌رود. خواندن note مجدداً مجوز جاری آن را داخل تراکنش بررسی می‌کند.
- API پیام‌ها آخرین۵۰پیام مجاز را می‌دهد؛ قبل از cursor معتبر، پیام‌های قدیمی‌تر قابل بارگذاری‌اند. page size پیش از فیلتر note محاسبه نمی‌شود. شمارش کل داخلی یا «آخرین پیام» داخلی به مشتری داده نمی‌شود.
- خروج/تغییر نشست یک nonce بدون اطلاعات شخصی را بین تب‌ها پخش می‌کند. صندوق مشتری/مدیر داده و draft قبلی را پاک و اعتبار را دوباره بررسی می‌کند؛ nonce حاوی cookie، متن یا شناسهٔ مشتری نیست. بازگشت به تب هم بازبینی می‌کند. پیام‌ها در localStorage ذخیره نمی‌شوند.
- درخواست و پیام کلید idempotency دارند؛ retry یکسان دوباره نمی‌سازد و استفادهٔ همان کلید برای متن/ترد دیگر 409 می‌دهد. کلید retry رابط هنگام خطای شبکه حفظ می‌شود؛ فقط پس از موفقیت پاک می‌شود.
- same-origin، ورودی strict، محدودیت طول/نرخ، سقف۱۰ترد باز، قفل مشترک کاربر هنگام ساخت/بازکردن و قفل ترد هنگام تغییر اجرا می‌شوند. متن کنترل نامعتبر رد می‌شود و HTML به‌صورت متن React نمایش داده می‌شود.
- migration022 مدل‌های SupportThread/SupportMessage، FK مالکیت سفارش و trigger پیام append-only/هویت ثابت ترد را اضافه کرده؛ روی DB محلی و kiya_test اعمال شده است. متن پیام در audit یا log کپی نمی‌شود؛ audit فقط actor/action/resource/message ID و دلیل تغییر وضعیت دارد.
- نمونهٔ اصلی قالب۳۶فایلی دست‌نخورده است. context قدیمیِ محلی ربات برای ارسال واقعی استفاده نمی‌شود؛ view دایرکت مستقیماً به API خصوصی وصل است.

## شواهد و بازتولید

۱۳۷ تست PostgreSQL/API پاس: ۱۰تست جدید حریم مشتری، note/cursor/metadata، MFA/scope/origin، retry/رقابت، بسته/بازکردن، pagination، مالکیت سفارش، تاریخچهٔ تغییرناپذیر، سقف ترد و تعلیق حساب؛ سایر۱۲۷تست قبلی هم پاس‌اند.

از `kiya-site/`: ابتدا `npm run test:wholesale:prepare`، سپس `npm run dev:ui-test` و در ترمینال دیگر `npm run test:support:browser`. این suite واقعاً از UI درخواست می‌سازد، reload و escaping، پاسخ کارمند، عدم نمایش note به مشتری/نقش فقط‌خواندنی، منع مشتری دیگر، close/reopen، موبایل و خروج در تب دیگر را بررسی می‌کند. تمام هویت‌ها و نوشته‌ها مصنوعی و روی localhost/kiya_test هستند. suite فقط fixture پشتیبانی و RateBucket همین DB تست را پاک می‌کند؛ دادهٔ عملیاتی هدف نیست. مشتری آزمایشی تازه دارد و cookie مشترک suite عمده را revoke نمی‌کند.

چهار suite مرورگر ورود دوحالته، حساب/نقش/MFA، پرداخت/ارسال و عمده نیز پس از این تغییرات پاس شدند. خروجی تست compiler جدا در `.next/ui-test` قرار می‌گیرد تا با build پیش‌نمایش مخلوط نشود؛ فایل‌ها ignored هستند. migrationهای اعمال‌شده ویرایش نشده‌اند.

## باقی‌مانده

تخصیص ترد به کارمند، SLA، جست‌وجوی پیشرفته، پیوست خصوصی، اعلان و اتصال پیام‌های پشتیبانی به Telegram هنوز ساخته نشده‌اند. این مرحله inbox پایهٔ واقعی را کامل می‌کند، نه تمام قرارداد F06 یا تمام سایت. CMS/استوری/کیامگ و مرجوعی/بازپرداخت همچنان کار دارند؛ نتیجهٔ محلی اثبات استقرار، Telegram واقعی یا خدمت حمل نیست.
