# تصمیم‌های معماری (ADR)

> هر تصمیم مهم را اینجا با فرمت کوتاه ثبت کن. ایجنت‌های کدنویسی موظف‌اند تصمیم‌های ضمنی خود را اینجا ثبت کنند.

## الگو

```
### ADR-000 — عنوان تصمیم
- تاریخ: ۱۴۰۵/مهر/۲۵
- وضعیت: پیشنهادی | پذیرفته | رد‌شده | جایگزین‌شده
- زمینه: چه مشکلی بود؟
- گزینه‌ها: الف / ب / ج
- تصمیم: کدام و چرا
- پیامد: چه چیزی ساده‌تر شد، چه چیزی سخت‌تر
```

---

### ADR-001 — فید «پست‌محصول» به‌جای صفحهٔ محصول به‌عنوان مسیر اصلی
- وضعیت: پذیرفته
- زمینه: نرخ افت بالا هنگام انتقال کاربر از شبکهٔ اجتماعی به صفحهٔ محصول خشک.
- گزینه‌ها: (الف) فروشگاه کلاسیک با کارت محصول (ب) فید اجتماعی + صفحهٔ محصول ثانویه (ج) فقط فید.
- تصمیم: **ب** — فید مسیر کشف و تبدیل است؛ `/product/[slug]` برای SEO و خریدار هدف‌مند باقی می‌ماند.
- پیامد: + نرخ تبدیل درون‌برنامه‌ای، − نیاز به دو تجربهٔ هم‌زمان نگه‌داری‌شده با یک منبع داده.

### ADR-002 — کامنت‌ها فقط یک سطح ریپلای
- وضعیت: پذیرفته
- زمینه: تودرتویی بی‌نهایت هم UI را می‌شکند هم مدل داده را سنگین می‌کند.
- تصمیم: ریپلای تخت با منشن `@نام` (الگوی اینستاگرام).
- پیامد: + سادگی کوئری و UI، − گفت‌وگوهای عمیق باید به دایرکت منتقل شوند (که قابلیت آن هست).

### ADR-003 — پول با `Decimal(14,0)` تومان
- وضعیت: پذیرفته
- زمینه: خطای گرد‌کردن float در مبالغ میلیونی.
- تصمیم: `Decimal` در DB، محاسبه فقط سرور، فرمت نمایش در کلاینت.
- پیامد: + صحت مالی، − نیاز به تبدیل در لبهٔ API.

### ADR-004 — RBAC در مدل داده از روز اول
- وضعیت: پذیرفته
- زمینه: افزودن نقش‌بندی بعد از ساخت پنل، بازنویسی گسترده می‌خواهد.
- تصمیم: `Role/RolePermission/UserRole/ScopeGrant` در اسکیمای اولیه + `requirePermission` در همهٔ Server Actionها.
- پیامد: + امنیت و انعطاف، − هزینهٔ اولیهٔ بیشتر در فاز ۲.

### ADR-005 — رزرو ۱۰ دقیقه‌ای موجودی در ورود به پرداخت
- وضعیت: پذیرفته
- زمینه: oversell در فروش‌های ناگهانی.
- تصمیم: افزایش `reserved` هنگام ساخت قصد پرداخت + job آزادسازی + کاهش `stock` فقط در پرداخت موفق.
- پیامد: + عدم فروش بیش از موجودی، − موجودی قابل‌فروش موقتاً کمتر از فیزیکی است.

### ADR-006 — SSE به‌جای WebSocket در MVP
- وضعیت: پذیرفته
- زمینه: کامنت لایو، شمارندهٔ سبد و وضعیت سفارش نیاز به پوش دارند؛ WebSocket در محیط serverless گران/پیچیده است.
- تصمیم: SSE برای جریان‌های یک‌طرفه؛ چت پشتیبانی در MVP با polling کوتاه + SSE، ارتقا به WebSocket در فاز ۷.
- پیامد: + سادگی استقرار، − نیاز به ارتقا برای چت دو‌طرفهٔ پرحجم.


### ADR-007 — مرجع بازبینی و نسخه‌بندی تحویل
- تاریخ: 2026-10-22
- وضعیت: پیشنهادی برای تأیید مالک؛ خط مبنای این بسته
- زمینه: تعارض نسخه‌ها، multi-tenancy، نقش ADMIN و معماری صف در اسناد اولیه.
- تصمیم پیشنهادی: قرارداد ۰۰ و ۱۰/۱۱ مقدم؛ V1 تک‌فروشنده با OTP checkout، pg-boss و فقط OWNER برای مدیریت نقش. تکمیل‌های V1.1/V2/V3 جدا.
- پیامد: جلوگیری از scope creep و ادعای قابلیت پیاده‌نشده؛ تغییر با تصمیم صریح مالک و ثبت ADR جدید.

### ADR-008 — ماکاپ به‌عنوان مرجع بصری، نه زیرساخت تولید
- تاریخ: 2026-10-22
- وضعیت: پذیرفته برای مستندسازی وضعیت فعلی
- زمینه: HTML مستقل دارای handlers محلی، CDN و پیام موفقیت نمایشی است.
- تصمیم: نمونه‌ها حفظ شوند؛ source of truth خرید/مجوز سرور آینده و معیار سند ۱۲ است. schema Markdown قرارداد اولیه است، نه migration معتبر.
- پیامد: دمو بدون از دست رفتن مرجع طراحی حفظ می‌شود؛ سازنده ملزم به ارائهٔ شواهد تست واقعی است.


### ADR-009 — هویت قطعی KIYA و عمده در هسته
- تاریخ: 2026-10-22
- وضعیت: پذیرفته بر اساس پیام مستقیم مالک
- تصمیم: نام کیا — KIYA، دامنه kiyaco24.ir، شناسه‌های عمومی kiyaco24/kiyaco24bot و لوگوهای ارسالی، بنفش/طلایی. همکار تأییدشده با خرید جینی و قیمت محرمانه بخشی از هسته است. هدف تحویل FULL با مراحل میانی است.
- پیامد: اصلاحیه۱۴..۱۸ بر نام/رنگ/فازهای قدیمی مقدم؛ صرف همراه‌داشتن فایل env، اتصال واقعی نیست.

### ADR-010 — مراجع قدیمی بدون انتقال ادعای انجام‌شدن
- تاریخ: 2026-10-22
- وضعیت: پذیرفته برای ثبت واقعیت مخزن
- تصمیم: هر دو سند تاریخی حفظ و نیازهای تازه با قرارداد FULL تطبیق شوند؛ claimهای done/live نیازمند کد و شواهد‌اند. انتخاب D1 در مرجع قدیمی با مبنای Postgres یکی فرض نشود.
- پیامد: کیامگ/گردونه/کیف/مینی‌اپ/چت checkout حذف نمی‌شوند؛ تکمیل اتصال‌ها و فعال‌سازی حقوقی باید مستقل اثبات شود.


### ADR-011 — بسته‌شدن دامنهٔ لباس و حداقل عمده
- تاریخ: 2026-10-22
- وضعیت: پذیرفته با دستور مستقیم مالک
- تصمیم: لباس معمولی خارج، لباس زیر داخل کاتالوگ؛ حداقل عمده یک جین و بدون حداقل مبلغ اضافه. policy تأییدشدهٔ config مرجع seed است؛ runtime پس از setup و دادهٔ واقعی فعال می‌شود.
- پیامد: نیاز به تأیید دوبارهٔ این موارد نیست؛ price/pack واقعی همچنان دادهٔ عملیاتی لازم است. درخواست دخانی/نیکوتینی ثبت، اما امکانات فروش آن خارج از محدودهٔ ساخت حاضر است.

### ADR-012 — مرحلهٔ اول قابل اجرا، بدون وانمودکردن backend
- تاریخ: 2026-10-22
- وضعیت: پذیرفته برای اجرای مرحله‌ای
- تصمیم: Next.js 16.4.2/React 19.3.1 سازگار با Node22 و lockfile؛ ابتدا رابط قابل بررسی و تست مرورگر، با data-demo و noindex. Local UI store با useSyncExternalStore فقط برای preview؛ نه جایگزین Postgres یا state مالی.
- پیامد: طرح قابل لمس و تست است؛ CM/WH/CO تا backend حقیقی تکمیل‌شده محسوب نمی‌شوند. PostgreSQL و استک اصلی حفظ می‌شود؛ هیچ SQLite موازی برای مالی ساخته نشد. موارد FULL به گزارش۲۱ منتقل شده‌اند و حذف نشده‌اند.

### ADR-013 — PostgreSQL و اختیار سرور، با demo جدا از هویت واقعی
- تاریخ: 2026-10-22
- وضعیت: پیاده‌شده در مرحلهٔ دوم؛ نه اعلام آمادگی تولید
- تصمیم: PostgreSQL واقعی + Prisma7/adapter-pg؛ migrations SQL تراکنشی با ledger/checksum و advisory lock، چون native engine میزبان خارجی در sandbox مسدود است. Client/validate از WASM موجود npm تولید می‌شود؛ prisma migrate deploy تا baseline رسمی مجاز نیست.
- تصمیم: cookie opaque/hash در DB، MFA اجباری برای مدیریت، مجوزهای DB؛ login آزمایشی synthetic فقط در demo و هیچ phone-verified جعلی. owner بدون رمز پیش‌فرض و فقط bootstrap محلی یک‌بار؛ اطلاعات مشتری واقعی و provider هنوز فعال نیست.
- پیامد: CM عمومی و پروندهٔ WH به DB وصل‌اند؛ پسند/سبد هنوز محلی و WH pricing/order ساخته‌نشده است. پنل، RBAC پایه و TOTP به معنی تکمیل FULL/admin scope یا ممیزی امنیت نیستند. شواهد و حدود در گزارش۲۲ است.

### ADR-014 — مدیر کل سروری و تفکیک نمایش از اختیار
- تاریخ: 2026-10-22
- وضعیت: اجراشده در نسخه0.4.0؛ نه تأیید تولید
- تصمیم: حساب درخواست‌شده فقط در DB محلی، با hash رمز و phone ثبت‌شده ولی تأییدنشده؛ هیچ credential شخصی در seed/Git نیست. OWNER + MFA برای IAM، نقش پایه تغییرناپذیر، custom-role فقط مجوز عملیاتی، ارتقای مالک با تأیید صریح.
- تصمیم: serialize عملیات IAM با advisory lock، reauthorization/session/actor row-lock داخل transaction؛ version، last-owner/self guard و audit؛ تغییر نقش/وضعیت/رمز، نشست‌های مربوط را باطل می‌کند.
- پیامد: مدیریت تیم و نقش‌ها اجرایی‌اند؛ scope کالا/انبار، دعوت/بازیابی، reset MFA، تولید و فروش واقعی تکمیل نشده‌اند. گزارش۲۴ مرجع حدود و شواهد است.

### ADR-015 — کاتالوگ DB و موجودی بدون وانمودکردن commerce
- تاریخ: 2026-10-22
- وضعیت: اجراشده در نسخه0.5.0؛ نه تکمیل FULL
- تصمیم: فقط PUBLISHED به DTO عمومی با قیمت خرده و boolean دسترسی موجودی می‌رود؛ هیچ شمارش دقیق انبار/قیمت خصوصی در RSC یا API عمومی نیست. fixtures فقط seed/preview و در live مخفی‌اند. پست ناموجود/بایگانی قبل streaming با proxy404 کنترل می‌شود.
- تصمیم: تغییر metadata/رنگ فقط DRAFT با version؛ تغییر وضعیت جداگانه و audited. نسخهٔ کالا از نسخهٔ SKU جداست؛ stock correction نسخهٔ SKU را تغییر می‌دهد، نه metadata. packSize صرفاً مشخصه است؛ BOM/quote/reservation/order نیست.
- تصمیم: Stock ledger append-only + Product→Variant lock order + UUID advisory lock برای retry، بررسی session/permission داخل transaction و قواعد stock/reserved. عکس معتبر decode/re-encode و EXIF حذف، با hash محلی و gate تصویر draft؛ volume/backup/quota/object-storage پیش‌نیاز تولید است.
- پیامد: مسیر ثبت تا انتشار واقعی و تست‌شده است؛ multiwarehouse، BOM واقعی، قیمت خصوصی عمده، سفارش/پرداخت، نگهداری رسانه و باقی FULL باز هستند. گزارش۲۵ مرجع شواهد و حدود است.
