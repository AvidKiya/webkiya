# ۳۵ — آماده‌سازی، ارسال و پیگیری سفارش

2026-10-24 · شاخهٔ `arena/2c244362-webkiya` · توسعهٔ سایت مستقل، بدون استقرار خارجی.

## مسیر استفاده

مالک/MFA ← پنل ← «پردازش و ارسال سفارش‌ها» (`/admin/orders`). فهرست سفارش‌های PAID با فیلتر وضعیت و صفحات۲۰تایی، اقلام snapshot سفارش و تعداد ترکیب جین، نشانی ثبت‌شدهٔ پرداخت و مبلغ سروری نمایش داده می‌شود. اطلاعات حساس بانک/رسید/Telegram ID به DTO ارسال وارد نمی‌شوند. لینک عمومی مدیریت به ویترین اضافه نشده است.

۱. سفارش با پرداخت CONFIRMED و وضعیت مالی PAID → شروع آماده‌سازی با دلیل حداقل۱۰نویسه.
۲. PREPARING → ثبت ارسال با شرکت حمل، کد رهگیری۴تا۸۰کاراکتر و دلیل.
۳. SHIPPED → ثبت تحویل با تأیید صریح UI و مستند در دلیل. تأییدِ تحویل، اظهار مسئول مجاز است؛ اتصال شرکت حمل یا مدرک خودکار جعل نشده است.

مشتری در «حساب و سفارش‌های من» فقط رهگیری همان سفارش متعلق به خود، وضعیت، شرکت حمل و زمان‌های ثبت ارسال/تحویل را می‌بیند. کد رهگیری متن است؛ URL یا JavaScript ارسالی مدیر به لینک تبدیل نمی‌شود. همکار/خرده از همان مسیر عبور می‌کنند؛ موجودی قبلاً هنگام capture پرداخت کسر شده و این عملیات دوباره موجودی یا وجه را تغییر نمی‌دهد.

## اختیار و یکپارچگی

- `order:read` برای فهرست و آدرس ارسال؛ `order:manage` برای تغییر وضعیت. نقش خواندنی می‌تواند بدون دیدن رسید/اختیار مالی تعریف شود و فرم نوشتن نمی‌بیند. برای کاربر عملیاتی هر دو مجوز را تخصیص دهید. permission مالی به‌تنهایی اختیار ارسال نیست.
- Session سروری، MFA، same-origin، schema strict، محدودیت نرخ، بازبینی مجوز در تراکنش، قفل سفارش، version و audit اجرا می‌شوند.
- `OrderShipment` جدا از وضعیت مالی سفارش است؛ تنها یک رکورد برای هر سفارش. هیچ تغییر صوری PAID به SHIPPED در ledger مالی نداریم.
- migration020 جدول/constraint/trigger و مجوزهای مالک را اضافه کرد. migration021 اشتباه تطبیق نام وضعیت پرداخت را اصلاح کرد: **ManualPayment.CONFIRMED** و **PurchaseOrder.PAID** باید هر دو برقرار باشند. migration اعمال‌شده ویرایش نشد. هر دو روی DB محلی و kiya_test اعمال شدند.
- DB حذف تاریخچه، ردکردن مراحل، نوشتن version غلط، تغییر هویت سفارش یا بازنویسی شرکت حمل/رهگیری پس از ارسال را رد می‌کند. تحویل نهایی قابل ویرایش نیست. تصحیح استثنایی/مرجوعی جریان مستقلی می‌خواهد که هنوز ساخته نشده؛ دورزدن trigger راه کاربری نیست.
- اعطای مجوز جدید فقط به Role موجود OWNER در migration است؛ نقش محدود دیگر خودکار مجوز نمی‌گیرد. permissionVersion مالکان موجود افزایش یافته و نشست قبلی برای ورود مجدد نامعتبر می‌شود. MFA حذف/بازنشانی نشده است.

## شواهد

۱۲۷ تست واقعی PostgreSQL/API پاس: ۷تست تازهٔ اختیار/MFA/origin، منع ارسال بدون پرداخت در API و DB، ترتیب مراحل، رقابت و stale version، حریم رهگیری، نقش فقط‌خواندنی و منع دستکاری مستقیم DB. تعدادهای قبلی/موجود در این مجموع هستند.

مرورگر `npm run test:telegram-payment:browser` اکنون پس از خرید/رسید/تطبیق مصنوعی، از UI واقعی مدیر آماده‌سازی و ارسال و تحویل را ثبت می‌کند، نمایش رهگیری در حساب مشتری را پس از reload بررسی می‌کند و نبود overflow موبایل را می‌سنجد. دو suite ورود دوحالته و حساب/نقش/MFA نیز پاس شدند. provider، بانک، حمل و هویت این آزمون‌ها مصنوعی‌اند؛ پول، مرسوله یا پیام واقعی ارسال نشده است.

بازسازی از `kiya-site/`: `npm run test:wholesale:prepare`، سپس `npm run dev:ui-test` و در ترمینال دیگر سه suite مرورگر. آماده‌سازی تست فقط روی kiya_test مجاز است؛ از seed/reset تست روی دادهٔ عملیاتی استفاده نشود.

## محدودهٔ باقی‌مانده

این تکمیلِ چرخهٔ پایهٔ سفارش است، نه تکمیل همهٔ سایت: بازپرداخت/مرجوعی، حمل خودکار، CMS/استوری/کیامگ و inbox خصوصیِ سروری هنوز کار دارند؛ قابلیت مالی مشروط یا محتوای نمایشی نباید واقعی اعلام شود. استقرار و اتصال Telegram واقعی همچنان جدا از نتایج محلی است. قالب اصلی۳۶فایلی و سیاست MFA/قیمت عمدهٔ خصوصی حفظ شده‌اند.
