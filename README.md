# کیا — KIYA

**شروع مستقل از خود قالب مالک:** پروژهٔ جدید در [`kiya-site/`](kiya-site/README.md) است؛ اصل قالب، رابط جدید و بک‌اند/اسناد در یک پوشه نگهداری می‌شوند. رابط جدید روی3100 اجرا می‌شود. هنوز همهٔ فرم‌های قالب به بک‌اند متصل نیستند؛ [وضعیت دقیق](kiya-site/IMPLEMENTATION.md). پروژهٔ قبلی زیر حفظ شده است.

فروشگاه اجتماعی فارسی با هویت بنفش/طلایی.

**برای دیدن پنل بدون رمز:** مسیر `/admin/preview` یا لینک «دیدن مدیریت» بالای فروشگاه؛ صرفاً رابط فقط‌خواندنی با نمونه‌های محلی است، نه ورود مدیر یا نمایش اطلاعات خصوصی. مسیر `/admin` همچنان رمز و MFA می‌خواهد.

**نسخهٔ جاری0.11.0:** قالب انتخابی شما به سایت Next/PostgreSQL متصل است؛ ورود/MFA، مدیریت، کاتالوگ و قیمت خصوصی، سبد و سفارش اولیه با رزرو کوتاه‌مدت حفظ شده‌اند. پرداخت و ارسال فعال نیست و انتشار تولید انجام نشده است. [نقشهٔ جاری](file/docs/26-delivery-map.md) و [گزارش اتصال قالب](file/docs/31-selected-template.md) مرجع وضعیت‌اند؛ بخش‌های نسخه‌دار پایین، تاریخچهٔ توسعه‌اند.

## Cloudflare: آماده‌سازی، نه استقرار انجام‌شده

بستهٔ Workers، R2/Images خصوصی، cron رزرو، CI و مسیر انتشار امن آماده و محلی تست شده‌اند؛ **در حساب شما deploy نشده است**. دسترسی API کلادفلر و تنظیم GitHub Secrets از این محیط مسدود است؛ PostgreSQL خارجی، bucket واقعی و کلیدهای اجرای اصلی هم هنوز تحویل نشده‌اند. حساب/دیتابیس خصوصی قبلی در این محیط بازیابی‌شده موجود نبود؛ نمونهٔ محلی را حساب اصلی ندانید. [پیش‌نیازها و مراحل دقیق](file/docs/32-cloudflare-deployment.md).

## اجرای محلی

Node.js 22 و npm، در دو ترمینال:

```sh
npm ci
npm run db:local
```

ترمینال دوم، پس از پیام آماده‌بودن PostgreSQL:

```sh
npm run db:migrate
npm run db:seed
npm run dev -- --port 3000
```

`db:local` یک **PostgreSQL واقعی** از باینری npm اجرا می‌کند، نه SQLite یا شبیه‌ساز؛ فقط روی `127.0.0.1:55432`. داده در `.data/postgres` و اسرار تصادفی در `.env.local` ذخیره می‌شوند؛ هر دو از Git خارج‌اند. اگر `.env.local` از قبل وجود دارد، آن را بدون بررسی پاک نکن؛ [قالب تنظیمات](.env.example) را با محیط خود تطبیق بده. PostgreSQL در ترمینال اول باید روشن بماند. این ابزار مخصوص توسعه است، نه زیرساخت تولید.

برای خروجی تولیدیِ **همین محیط آزمایشی**: `npm run build` سپس `npm run start -- --port 3000`. وب‌سرور به `0.0.0.0` متصل می‌شود و previewهای `e2b.app` مجازند؛ مرورگر برای APIها فقط آدرس نسبی استفاده می‌کند. فونت و تصاویر محلی‌اند.

## آنچه کار می‌کند

- فید/اکسپلور RTL واکنش‌گرا، روشن/تیره، جست‌وجو و فیلتر، استوری، پست مستقیم/مودال و توضیح بیشتر/کمتر.
- دیدگاه و پاسخ **عمومی در PostgreSQL**، صفحه‌بندی دیدگاه و پاسخ‌ها، حذف فقط توسط نویسنده، پنهان‌سازی توسط پرسنل مجاز؛ retries با کلید idempotency.
- نشست opaque با token تصادفی و hash در DB، کوکی HttpOnly/SameSite، خروج و ابطال سروری، محدودیت نرخ در DB و کنترل Origin برای mutation.
- `/account`: ورود **صریحاً آزمایشی** فقط به حساب مصنوعی مشتری؛ نه SMS یا تأیید هویت. شماره یا اطلاعات شخصی واقعی وارد نکن.
- درخواست همکاری، وضعیت پایدار و بررسی با دلیل، کنترل نسخه، منع self-approval و ثبت audit.
- `/admin`: ورود رمز + TOTP، seed رمزگذاری‌شده، جلوگیری از بازپخش کد و هشت کد بازیابی یک‌بارمصرف. قبل MFA هیچ دادهٔ مدیریت ارائه نمی‌شود.
- مجوزهای سروری و نقش‌های پایهٔ مالک/پشتیبانی/محتوا؛ داشبورد با شمارش DB، moderation و بررسی همکار، فهرست خواندنی محصولات/تیم/audit مطابق مجوز.
- پسند، ذخیره و سبد همچنان **محلی** هستند. دیدگاه‌های محلی قدیمی خودکار منتشر یا به سرور منتقل نمی‌شوند.

## ساخت امن مالک اولیه

**هیچ مالک یا رمز پیش‌فرضی در seed وجود ندارد.** حساب مدیر کلِ همین محیط با درخواست مستقیم مالک، فقط در دیتابیس محلی راه‌اندازی شده است؛ شماره و رمز او جزو سورس، مستندات یا Git نیستند. روی clone/DB تازه باید bootstrap مستقل انجام شود. اگر مالک موجود باشد این ابزار او را تغییر یا reset نمی‌کند. این کار فقط یک بار، با دسترسی محلی مورد اعتماد انجام می‌شود. در Bash، رمز را بدون نمایش و بدون قرار دادن در history/آرگومان بگیر:

```sh
read -r -s -p 'Owner password (14+ characters): ' KIYA_OWNER_PASSWORD; echo
export KIYA_OWNER_PASSWORD
npm run owner:create -- --handle kiya-owner --name 'مالک کیا'
unset KIYA_OWNER_PASSWORD
```

برای ورود `/admin` یا «ورود مدیر کل» بالای فروشگاه. شناسهٔ پرسنلی یا شمارهٔ موبایل ثبت‌شده (فارسی/انگلیسی، 09… یا +98…)، رمز، سپس تنظیم Authenticator و تأیید TOTP. ثبت شماره با bootstrap/مدیر به معنی تأیید پیامکی نیست. کدهای بازیابی فقط یک بار نمایش داده می‌شوند؛ خارج از مرورگر امن نگه دار. برای اتصال شمارهٔ موبایل در bootstrap، آرگومان اختیاری `--phone` را از متغیر محلیِ خودتان بدهید؛ مقدار شخصی را در source یا مثال عمومی ثبت نکنید. رمز/کلید/کد بازیابی را در Git یا چت نفرست. ابزار مالک موجود را جایگزین یا reset نمی‌کند. کلید `MFA_ENCRYPTION_KEY` باید پایدار، پشتیبان‌گیری‌شده و امن بماند؛ تغییر خودسرانهٔ آن MFA را از کار می‌اندازد.

## آزمون‌ها

```sh
npm run db:test:create
npm run db:migrate:test
npm run db:seed -- --test
npm run prisma:validate
npm run lint
npm run typecheck
npm test
npm run test:backend
npm run build
npm run test:e2e
python3 file/scripts/validate_package.py
python3 -m unittest discover -s file/scripts -p 'test_*.py'
npm audit --omit=dev
```

- ۱۲ unit، ۶۷ تست یکپارچه روی PostgreSQL واقعی و ۱۰ E2E مرورگر.
- تست بک‌اند فقط DB جداگانهٔ `kiya_test` را می‌پذیرد و دادهٔ **همین DB تست** را پاک می‌کند؛ هرگز از نام `kiya_test` برای دادهٔ واقعی استفاده نکن.
- E2E فقط در محیط demo محلی اجرا شود: مشتری مصنوعی ثبت می‌کند و برای بررسی MFA یک پرسنل موقت با نقش محدود می‌سازد و حذف می‌کند؛ مالک پیش‌فرض نمی‌سازد. دادهٔ نمونهٔ دیدگاه/درخواست مشتری در demo می‌ماند.
- Playwright خروجی build را روی 3000 اجرا می‌کند یا سرور محلی موجود را استفاده می‌کند؛ بعد تغییر کد، build و restart لازم است. Chromium Linux x64 از npm تأمین می‌شود و CDN لازم ندارد.
- workflow شامل سرویس PostgreSQL 16 نوشته شده؛ نتیجهٔ اجرای GitHub را باید مستقل بررسی کرد.

## مهاجرت و محدودیت محیط

Prisma 7 با adapter استاندارد `pg` استفاده می‌شود. Client با compiler WASM موجود در npm تولید می‌شود؛ native schema-engine از شبکهٔ این sandbox قابل دانلود نیست. helper فقط `generate/validate` را اجرا می‌کند؛ جای engine برای migrate را جعل نمی‌کند.

**فرمان پشتیبانی‌شدهٔ migration در این مرحله `npm run db:migrate` است**: SQL نسخه‌دار، transaction، advisory lock و checksum با ledger مستقل `kiya_schema_migrations`. از `prisma migrate deploy/reset` روی این DB استفاده نکن؛ ledger آن ابزار در این مرحله baseline نشده است. SQL شامل constraint و triggerهایی فراتر از مدل Prisma است. نسخه‌های اعمال‌شده را تغییر نده؛ migration جدید بساز. در محیط توسعهٔ این sandbox PostgreSQL 18.4 اجرا شده؛ CI برای PostgreSQL 16 تنظیم شده، نه اینکه اجرای 16 از قبل اثبات شده باشد.

`npm run db:maintenance` bucketهای منقضی و نشست‌های منقضیِ بیش از ۳۰ روز را پاک می‌کند؛ زمان‌بندی آن هنوز با supervisor/cron انجام نشده است. audit به‌صورت خودکار حذف نمی‌شود.

## هنوز تکمیل نشده

OTP واقعی/بازیابی مشتری، دعوت/بازیابی و حذف کامل چرخهٔ عمر پرسنل، scopeهای ریزدانه، چرخهٔ کامل محتوای اجتماعی کالا/گالری و سایزبندی، قیمت خصوصی عمده/BOM، انبار چندشعبه/رزرو سفارش، سبد سروری، quote/reservation/order/payment، اتصال پیامک/تلگرام و بقیهٔ ماژول‌های FULL. تأیید همکار **قیمت عمدهٔ ساختگی یا مجوز مدیریت ایجاد نمی‌کند**؛ تا لیست قیمت واقعی متصل نشود فقط وضعیت پرونده دیده می‌شود. MOQ یک جین و بدون کف مبلغ حفظ شده است.

پنج کالای اولیه و قیمت/تصویر آن‌ها نمونه‌اند و در live از ویترین حذف می‌شوند؛ کالاهای جدید مدیریت در DB پایدارند، اما سفارش آنلاین خاموش است. قبل داده یا پرداخت واقعی: ممیزی امنیت، DB runtime با حداقل مجوز جدا از migration-owner، backup/restore، مانیتورینگ/نگهداری، provider و آزمون‌های مالی لازم است. trigger audit در برابر حساب برنامه مانع update/delete عادی است، نه DBA یا مالک DB. اتصال local در این مرحله مالک DB است. `APP_MODE=live` و `ALLOW_DEMO_LOGIN=false` ورود و نشست‌های demo را می‌بندند، اما **به‌تنهایی سایت را آمادهٔ فروش نمی‌کنند**. Secure cookie در HTTPS و محیط تولیدِ غیر-demo فعال است؛ HTTP فقط برای demo محلی است. تنظیمات forwarded IP فقط پشت ingress کنترل‌شده مجاز است.

- این‌ها مجوز **عملیاتیِ سراسری** هستند، نه scope کالا یا انبار. فهرست پرسنل فعلاً سقف۱۰۰ دارد، حذف role/user، MFA reset و owner-transfer اختصاصی هنوز نیست. ممیزی امنیت و تولید همچنان لازم است.

## کاتالوگ و موجودی — نسخه0.5.0

- ویترین از کالاهای PUBLISHED دیتابیس خوانده می‌شود، نه آرایهٔ ثابت مرورگر. DTO عمومی شامل قیمت خرده و «موجود/ناموجود» است؛ نه SKU، تعداد دقیق stock/reserved، بهای خرید یا قیمت خصوصی عمده. `APP_MODE=live` نمونه‌ها را حذف می‌کند، نه اینکه پرداخت را فعال کند.
- مسیر مدیر: `/admin` ← MFA شخصی ← «کاتالوگ» ← ساخت پیش‌نویس ← «مشخصات، رنگ‌ها، موجودی و انتشار». عنوان/دسته/توضیح/تصویر/قیمت/تعداد واحد بسته را ثبت، رنگ با SKU یکتا اضافه و موجودی را با دلیل اصلاح کنید؛ سپس با دلیل منتشر کنید. ویرایش کالای منتشرشده نیازمند بایگانی و بازگشت به پیش‌نویس است. ناموجود هم می‌تواند در ویترین دیده شود.
- `product:publish`، `inventory:read` و `inventory:manage` مستقل‌اند؛ OWNER پیش‌فرض هر سه را دارد. ساخت نقش/اعطای مجوز فقط از مدیر کل واقعی. metadata بدون مجوز انبار تعداد موجودی را نشان نمی‌دهد؛ SKU شناسهٔ عملیاتی است، نه راز مالی.
- اصلاح موجودی با row-lock، version، idempotency UUID، جلوگیری از موجودی منفی/کمتر از رزرو، ledger تغییرناپذیر و audit اتمیک. موجودی اولیه واقعی کالاهای تازه صفر است؛ هیچ خرید/رزروی از سبد محلی ساخته نمی‌شود.
- بارگذاری JPG/PNG/WebP ثابت تا۵MB و۲۵MP، تبدیل/کاهش ابعاد و حذف EXIF. رسانه در `.data/media` و metadata آن در DB است؛ در Git نیست. `MEDIA_ROOT` اختیاری باید volume پایدار و backup هم‌زمان با DB داشته باشد. عکس پیش‌نویس فقط برای staff مجاز با MFA است، پس از انتشار عمومی؛ عکس منتشرشده را محرمانه فرض نکنید حتی پس از بایگانی.
- در E2E فقط محصول و مالک موقت خودِ تست پاک می‌شوند؛ cleanup دفتر موجودی با اتصال privileged محلی، session-local bypass و شرط audit همان actor انجام می‌شود، نه TRUNCATE جدول مشترک. این قابلیت از API برنامه قابل فراخوانی نیست. integration فقط DB تست را truncate می‌کند.
- [گزارش و مرزهای این مرحله](file/docs/25-catalog-and-inventory.md). migration005 افزوده شده؛ runner پروژه هر پنج SQL را با checksum نگه می‌دارد. حساب واقعی مدیر کل/MFA او تغییر نکرده است.

## قیمت خصوصی عمده — نسخه0.7.0

- `/admin` ← کاتالوگ ← پروندهٔ کالا ← «قیمت خصوصی عمده برای همکار مشخص». کالا باید منتشرشده، جین فعال و همکار معتبر باشد. نرخ هر واحد تومان برای همهٔ اجزای جین یکسان است؛ مبلغ جین سروری و integer محاسبه می‌شود. هیچ قیمت واقعی یا دادهٔ همکار از طرف seed ساخته نشده است.
- مجوزهای `wholesale:price:read/manage/publish` جدا هستند. **ثبت‌کننده حتی اگر OWNER باشد نمی‌تواند قیمت خودش را منتشر کند.** مدیر کل باید به پرسنل مورداعتمادِ دیگری با MFA شخصی، نقش بازبینی قیمت بدهد؛ نقش پیشنهادی شامل dashboard:read، product:read، wholesale:price:read/publish است. این مرحله حساب واقعی دیگری برای شما نمی‌سازد یا MFA شما را تنظیم نمی‌کند.
- پیش‌نویس/قیمت منتشرشده immutable است؛ بایگانی و جایگزین بسازید. یک قیمت منتشرشده برای هر همکار/جین مجاز است؛ قیمت منقضی هم پیش از جایگزینی باید archive شود. POST قیمت UUID idempotency دارد. حالت INQUIRY عدد قیمت صفر یا fallback نمی‌دهد.
- مشتری در `/wholesale` فقط قیمت معتبر تخصیص‌یافته به حساب خودش را می‌بیند: قیمت واحد عمده، یک جین و قیمت تکی سایت. این مقادیر در SSR/RSC و DTO عمومی نیستند. session/kind/phone-verification/APP_MODE و APPROVED/expiry و Pack/Product status/version در هر خواندن بررسی می‌شوند؛ live بدون OTP واقعی هنوز برای ورود مشتری آماده نیست.
- بخش همکاران پنل، «تنظیم اعتبار همکاری» با دلیل/version و partner:approve دارد. تاریخ گذشته دسترسی قیمت را می‌بندد، بدون جعل status EXPIRED؛ حالت اصلی پرونده می‌تواند APPROVED بماند. GET /api/partner فیلدهای expiresAt/privatePricingAvailable/orderReady دارد؛ pricingReady قدیمی هنوز checkout-ready نیست.
- جزئیات و مرزها: [گزارش۲۸](file/docs/28-private-wholesale-prices.md)، [نقشهٔ به‌روز](file/docs/26-delivery-map.md) و `/progress`. هنوز لیست گروهی/عمومی، tier و قیمت متفاوت اجزا، quote/reservation/order/payment/outbox ساخته نشده‌اند. migration008 افزوده شده؛ قبلی‌ها تغییر نکرده‌اند.

## قالب انتخابی مالک — نسخه0.10.0

قالب افزوده‌شده در commit `2970536`، پوشهٔ «کیایی که دوسش داشتم»، مبنای رابط فعلی است. اصل فایل‌ها بدون تغییر حفظ و تاریخچهٔ main در شاخهٔ کاری ادغام شد؛ برنامهٔ Next/PostgreSQL و داده‌های قبلی حذف یا با StoreContext آزمایشی جایگزین نشده‌اند.

هدر، ناوبری سه‌ستونه و پایین موبایل، توکن‌های بصری، کارت‌ها، میان‌فید عمده و `/profile` از طرح منتخب اقتباس و به مسیرهای واقعی وصل شده‌اند. `/basket` هم پوستهٔ منتخب دارد و `/account` تاریخچهٔ واقعی سفارش اولیه را نشان می‌دهد. پنل امن موجود حفظ و ظاهر کارت/ناوبری آن هماهنگ شده است؛ تمام تب‌های نمونهٔ پنل قالب، ماژول عملیاتی تلقی نمی‌شوند.

سورس قالب مرجع است، نه اپ دومِ production؛ از build/typecheck/lint و اسکن Tailwind ریشه کنار گذاشته شده و StoreContext/پرداخت/قیمت عمدهٔ ساختگی آن وارد bundle فعال نمی‌شود. اجرای پروژه همچنان از package.json ریشه است. [گزارش۳۱ و تطبیق اجزای قالب](file/docs/31-selected-template.md) و نقشه۲۶ مرجع جاری‌اند. تکمیل FULL همچنان هدف است؛ OTP، پرداخت، ارسال، CMS، دایرکت و سایر باقی‌مانده‌ها حذف نشده‌اند.
